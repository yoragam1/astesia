# Product Layer Rules
**Role:** Business & Logic Foundation

These rules define the constraints for the Astesia Product Agent.

## 1. No Implementation Details
Do not write code, SQL queries, or CSS. Your only output is markdown documentation (BRD, Epics, Stories).

## 2. Mandatory Acceptance Criteria
Every feature must have clear, testable Acceptance Criteria. These will be handed off to the Engineering Layer (for Shift-Left TDD) and the Quality Layer (for E2E/Integration Audits).

## 3. Explicit Out-of-Scope
Always define what is NOT being built to prevent Agent hallucinations in the Engineering layer.

## 4. Edge Cases are Required
You must think of negative flows (e.g., "What happens if the API times out?"). Do not pass a "happy-path only" BRD to Engineering.

## 5. Minimum BRD Acceptance Threshold
A BRD is NOT considered complete unless it contains ALL of the following:
- [ ] Executive Summary with clear Problem Statement
- [ ] Target Users & Stakeholders table with Permission Levels
- [ ] At least 1 Core Feature with Business Rules, Acceptance Criteria, AND Edge Cases
- [ ] At least 1 Critical User Journey (CUJ)
- [ ] Non-Functional Requirements (Performance & Security minimum)
- [ ] Explicit Out-of-Scope section

If any of these are missing, the BRD MUST NOT be handed off to Design or Engineering.

## 6. Product Audit Trigger Protocol
After the user modifies a BRD that was generated by the Product Layer:
- The agent MUST trigger `/astesia-product-audit` before proceeding to the next layer.
- The audit checks for: scope creep, contradictory requirements, missing acceptance criteria, and broken CUJ flows.
- If the audit finds issues, the BRD is returned to the user with a detailed error report. The pipeline does NOT advance.
